# Estructura y funcionamiento avanzado de DNS

En el apartado **3.1** vimos para qué sirve DNS, cómo se organizan los nombres, qué son las consultas recursivas e iterativas y cómo funciona la caché. Ahora profundizaremos en estos conceptos para interpretar respuestas DNS y comprender, más adelante, cómo se administran las zonas en Windows Server.

**Resultados de aprendizaje relacionados:** RA2, especialmente **CE c)** (estructura, nomenclatura y funcionamiento de sistemas jerárquicos) y **CE h)** (comprobación del servicio, que se completará con las prácticas de servidor).

## 1️⃣ Repaso de la jerarquía: dominios, subdominios y FQDN

Los nombres DNS se organizan de derecha a izquierda, desde la raíz hasta el nombre específico de un equipo o servicio.

```text
. (raíz)
└── es                  Dominio de nivel superior (TLD)
    └── empresa         Dominio
        ├── www         Nombre de un servicio
        └── ventas      Subdominio
            └── pc01    Nombre de un equipo
```

- `www.empresa.es.` es un **nombre de dominio completo (FQDN)**.
- `pc01.ventas.empresa.es.` también es un FQDN.
- El punto final representa la raíz. En el uso cotidiano suele omitirse.
- Un nombre como `pc01` no identifica por sí solo el dominio completo: puede depender del sufijo DNS configurado en el cliente.

:::info[Dominio y zona no significan exactamente lo mismo]
Un **dominio** es una parte del árbol de nombres. Una **zona** es la parte de ese árbol cuyos registros administra un conjunto de servidores DNS. Un dominio puede estar repartido entre varias zonas si se delegan subdominios.
:::

## 2️⃣ Delegación de dominios y servidores autoritativos

DNS es un sistema **distribuido**: no existe un único servidor que almacene todos los nombres de Internet.

Un servidor **autoritativo** dispone de los datos de una zona y puede responder sobre sus registros. Cuando una parte del espacio de nombres se administra por separado, se realiza una **delegación**.

Por ejemplo, la organización `empresa.test` puede administrar su zona principal y delegar `ventas.empresa.test` en otros servidores:

```text
Zona empresa.test
  ├── www.empresa.test
  ├── correo.empresa.test
  └── delegación de ventas.empresa.test
                    │
                    ▼
          Zona ventas.empresa.test
             ├── pc01
             └── pc02
```

La zona superior utiliza registros **NS** para indicar qué servidores son autoritativos para la zona delegada. En determinadas delegaciones también hacen falta direcciones auxiliares, llamadas *glue records*, para poder localizar esos servidores sin provocar una dependencia circular.

:::tip[Ejemplo práctico]
Que exista el subdominio `ventas.empresa.test` **no obliga** a crear una zona independiente. Solo será una zona diferente si se administra y delega como tal.
:::

## 3️⃣ Resolución directa y resolución inversa

La **resolución directa** busca información asociada a un nombre. El caso más habitual consiste en obtener una dirección IP a partir de un nombre:

```text
www.empresa.test  ── consulta A ──►  192.168.10.20
```

La **resolución inversa** parte de una dirección IP y busca el nombre asociado mediante un registro **PTR** (*Pointer*):

```text
192.168.10.20  ── consulta PTR ──►  www.empresa.test.
```

Ambas consultas son independientes. Que exista un registro A **no significa** que exista automáticamente un PTR; tampoco garantiza que la resolución inversa devuelva el mismo nombre.

### 🟩 ¿Cómo se forma el nombre inverso en IPv4?

Para la dirección `192.168.10.20` se invierte el orden de sus cuatro octetos y se añade `in-addr.arpa`:

```text
IP:                  192.168.10.20
Octetos invertidos:  20.10.168.192
Consulta PTR:        20.10.168.192.in-addr.arpa.
```

En una red `/24`, una zona inversa habitual para ese ejemplo es `10.168.192.in-addr.arpa`; dentro de ella, el registro del último octeto `20` puede apuntar a `www.empresa.test.`.

En IPv6 se utiliza `ip6.arpa` y se invierten **dígitos hexadecimales**, no bloques completos. Lo estudiaremos como ampliación; en el laboratorio empezaremos por IPv4.

:::warning[No confundas las direcciones privadas con los dominios públicos]
Un servidor DNS interno puede resolver nombres hacia direcciones privadas como `192.168.10.20`. No es necesario que los registros A o AAAA contengan direcciones públicas.
:::

## 4️⃣ Consultas recursivas e iterativas: qué hace cada servidor

En el apartado 3.1 distinguimos ambos tipos de consulta. La diferencia importante es **quién se encarga de obtener la respuesta**.

- **Consulta recursiva:** el cliente pide a su servidor DNS una respuesta final o un error. Si el servidor admite recursión, realiza el trabajo necesario para resolverla.
- **Consulta iterativa:** el servidor consultado puede proporcionar la respuesta que conoce o indicar otros servidores a los que acudir mediante una referencia (*referral*).

Cuando una respuesta no está en caché y el resolvedor debe recorrer la jerarquía pública, el proceso simplificado es:

```text
Cliente Windows
      │  1. Consulta recursiva: www.ejemplo.com
      ▼
Resolvedor DNS configurado
      │  2. Pregunta a la raíz: ¿quién conoce .com?
      ├────────────────────────► DNS raíz
      │◄──────────────────────── referencia a servidores .com
      │  3. Pregunta por ejemplo.com
      ├────────────────────────► DNS del TLD .com
      │◄──────────────────────── referencia a autoritativos
      │  4. Pregunta por www.ejemplo.com
      ├────────────────────────► DNS autoritativo
      │◄──────────────────────── respuesta con el registro
      ▼
Cliente recibe la respuesta
```

**Importante:** es un modelo simplificado. Un resolvedor puede tener datos en caché, usar reenviadores o seguir otros caminos según la configuración. Por eso no siempre se observan todas esas consultas.

## 5️⃣ Caché, TTL y respuestas que cambian

Un servidor DNS recursivo puede conservar respuestas temporalmente para responder más rápido a futuras consultas. El **TTL** indica cuánto tiempo puede mantenerse una respuesta en caché.

Ejemplo: si una respuesta llega con TTL `600` segundos, después de cuatro minutos su TTL restante sería aproximadamente `360` segundos, siempre que siga almacenada.

Si el administrador modifica el registro en el servidor autoritativo, algunos clientes pueden continuar viendo el dato anterior mientras conserven una respuesta válida en caché.

No debe confundirse:

- **Caché del cliente:** información temporal almacenada por el sistema operativo.
- **Caché del servidor DNS:** información temporal que puede reutilizar para responder a varios clientes.
- **Registros de una zona:** datos administrados por el servidor autoritativo; no son simplemente entradas de caché.

## 6️⃣ Primeras consultas DNS desde Windows

Podemos explorar las respuestas con `nslookup`, sin instalar todavía nuestro servidor DNS. Para las consultas a dominios públicos necesitamos que el equipo tenga acceso a un DNS que pueda resolverlos; si el laboratorio está aislado, **no deben interpretarse los fallos como errores del ejercicio**.

```powershell
ipconfig /all
nslookup www.example.com
nslookup -type=NS es.
nslookup -type=SOA es.
nslookup 8.8.8.8
```

| Comando | Qué se pretende observar |
|---|---|
| `ipconfig /all` | Servidores DNS configurados en Windows |
| `nslookup www.example.com` | Resolución directa |
| `nslookup -type=NS es.` | Servidores publicados como autoritativos para `.es` |
| `nslookup -type=SOA es.` | Información de autoridad de la zona |
| `nslookup 8.8.8.8` | Consulta inversa de una IP pública |

El resultado puede variar con el tiempo y según el servidor DNS consultado. En particular, `nslookup` **consulta DNS**, por lo que no es una prueba del contenido del archivo `hosts` (esa diferencia ya se comprobó en P01).
