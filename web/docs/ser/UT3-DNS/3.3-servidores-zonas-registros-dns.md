# Servidores, zonas y registros DNS

En el apartado **3.2** hemos estudiado la jerarquía DNS, las delegaciones, la resolución inversa y las consultas. Ahora veremos **qué servidores intervienen**, **cómo se organiza la información que administran** y **qué registros contienen las zonas DNS**.

Estos conceptos serán necesarios para las próximas prácticas: configuraremos **Windows Server como DNS primario**, **Ubuntu Server con BIND9 como secundario** y comprobaremos las respuestas desde **SER-Cliente (Windows)**.

**RA relacionado:** RA2. **Criterios principales:** c), d), f), g) y h). La instalación y las transferencias se realizarán en los apartados prácticos posteriores.

## 1️⃣ ¿Todos los servidores DNS hacen lo mismo?

No. Aunque todos participan en la resolución de nombres, sus funciones pueden ser distintas.

| Tipo o función | ¿Qué hace? | Ejemplo |
|---|---|---|
| **Autoritativo** | Responde con los datos de las zonas de las que es responsable | DNS que administra `empresa.test` |
| **Recursivo** | Busca una respuesta completa para un cliente, consultando otros servidores si es necesario | DNS utilizado por los equipos de una organización |
| **Caché** | Conserva temporalmente respuestas obtenidas anteriormente | Resolvedor que reutiliza una respuesta mientras no expire su TTL |
| **Reenviador (*forwarder*)** | Recibe consultas que otro servidor DNS le envía para que las resuelva | DNS interno que reenvía consultas externas a un DNS público |

:::info[Son funciones, no necesariamente máquinas diferentes]
Un mismo servidor puede ser **autoritativo para `empresa.test`** y, además, ofrecer **resolución recursiva** a los clientes de su red. La configuración determina qué funciones presta y a quién.
:::

## 2️⃣ Servidor primario y servidor secundario

Cuando administramos una **zona DNS**, podemos mantener sus datos en un servidor principal y distribuir copias a otros servidores.

- **Zona primaria estándar:** contiene una copia de la zona que puede modificarse administrativamente en ese servidor.
- **Zona secundaria:** contiene una copia **de solo lectura** que se obtiene mediante transferencias desde uno o varios servidores maestros.
- **Servidor autoritativo:** tanto el que aloja una zona primaria como el que aloja una zona secundaria pueden responder **con autoridad** sobre esa zona.

En nuestro laboratorio:

```text
                Zona empresa.test
                       │
          ┌────────────┴────────────┐
          │                         │
  SER-Servidor                  SER-DNS2
  Windows Server                Ubuntu + BIND9
  Zona primaria                 Zona secundaria
  Modifica registros            Recibe una copia
          │                         │
          └────────────┬────────────┘
                       │
                SER-Cliente
                Consulta DNS
```

:::warning[Primario no significa «el único que responde»]
El servidor secundario también puede responder consultas sobre la zona transferida. La diferencia fundamental es **dónde se realizan los cambios de la zona** y cómo llegan a los demás servidores.
:::

## 3️⃣ ¿Qué es una zona DNS?

Una **zona** es el conjunto de datos DNS que se administra como una unidad. En ella se almacenan los **registros de recursos** (*Resource Records*, RR) que permiten resolver nombres y localizar servicios.

### 🟩 Zonas de búsqueda directa

Permiten obtener información asociada a un **nombre**. Por ejemplo:

```text
Nombre consultado: intranet.empresa.test
Tipo solicitado: A
Respuesta: 192.168.10.20
```

### 🟧 Zonas de búsqueda inversa

Permiten consultar el **nombre asociado a una dirección IP**, mediante registros PTR. En IPv4 se utiliza el árbol `in-addr.arpa`.

```text
Dirección IP: 192.168.10.20
Nombre consultado: 20.10.168.192.in-addr.arpa.
Tipo solicitado: PTR
Respuesta: intranet.empresa.test.
```

:::tip[Recuerda]
Un registro A y un registro PTR **no se crean automáticamente uno a partir del otro en todos los sistemas**. La coherencia entre resolución directa e inversa depende de los registros realmente configurados.
:::

## 4️⃣ Los registros de recursos (RR)

Cada registro DNS indica un dato sobre un nombre. Los más importantes para nuestra unidad son:

| Registro | Función | Ejemplo conceptual |
|---|---|---|
| **A** | Asocia un nombre a una dirección **IPv4** | `www → 192.168.10.20` |
| **AAAA** | Asocia un nombre a una dirección **IPv6** | `www → 2001:db8::20` |
| **CNAME** | Define un alias que apunta a otro **nombre DNS** | `intranet → web.empresa.test.` |
| **MX** | Indica qué servidores reciben el correo del dominio y su prioridad | `empresa.test. → 10 correo.empresa.test.` |
| **NS** | Indica servidores de nombres autoritativos de una zona o delegación | `empresa.test. → dns1.empresa.test.` |
| **PTR** | Asocia un nombre de búsqueda inversa con un nombre DNS | `20.10.168.192.in-addr.arpa. → web.empresa.test.` |
| **SOA** | Identifica información administrativa y parámetros de la zona | Servidor principal, contacto, número de serie y temporizadores |

**Importante:** las direcciones privadas como `192.168.10.20` son perfectamente válidas en un **DNS interno**. No es necesario utilizar direcciones públicas para nuestros registros A.

### 🟩 Registros A y AAAA

Se usan cuando necesitamos localizar un equipo o servicio mediante su dirección IP.

```text
web.empresa.test.       A       192.168.10.20
web.empresa.test.       AAAA    2001:db8::20
```

`2001:db8::/32` es un prefijo reservado para documentación; no representa una dirección pública operativa de nuestro laboratorio.

### 🟧 Registro CNAME: alias

Un alias permite ofrecer otro nombre para un servicio:

```text
web.empresa.test.       A       192.168.10.20
intranet.empresa.test.  CNAME   web.empresa.test.
```

Al consultar `intranet.empresa.test`, el DNS indica que es un alias de `web.empresa.test`. El cliente puede continuar la resolución hasta obtener una dirección.

:::warning[CNAME no apunta directamente a una IP]
El destino de un CNAME es **otro nombre DNS**, no una dirección IPv4. Además, un nombre que tenga un CNAME no debe tener otros registros de datos ordinarios con ese mismo nombre.
:::

### 🟥 Registro MX: correo electrónico

Un registro MX indica los servidores encargados de recibir el correo de un dominio:

```text
empresa.test.           MX      10 correo1.empresa.test.
empresa.test.           MX      20 correo2.empresa.test.
correo1.empresa.test.   A       192.168.10.30
correo2.empresa.test.   A       192.168.10.31
```

El valor numérico es la **preferencia**: normalmente se intenta primero el MX con **número menor**. Los destinos MX deben ser nombres de servidores, no direcciones IP, y no deben ser alias CNAME.

### 🟪 Registros NS y SOA

- **NS:** identifica los servidores DNS autoritativos de la zona o establece una delegación.
- **SOA (*Start of Authority*):** contiene los datos de control de una zona, necesarios, entre otras cosas, para gestionar actualizaciones de zonas secundarias.

### 🟦 Registro PTR

Se utiliza en la resolución inversa. Por ejemplo, el PTR asociado a `192.168.10.20` puede devolver `web.empresa.test.`.

## 5️⃣ El registro SOA y la sincronización de zonas

El registro **SOA** es especialmente importante cuando existen zonas secundarias, como ocurrirá en nuestro laboratorio.

| Campo | Significado práctico |
|---|---|
| **Servidor principal (MNAME)** | Nombre del servidor principal indicado en el SOA |
| **Contacto (RNAME)** | Dirección de contacto representada con sintaxis DNS |
| **Serial** | Número de versión de los datos de la zona |
| **Refresh** | Intervalo orientativo para comprobar si la zona ha cambiado |
| **Retry** | Tiempo antes de reintentar tras un fallo de actualización |
| **Expire** | Tiempo tras el cual un secundario deja de considerar válida una zona si no consigue actualizarla |
| **Minimum / TTL negativo** | Valor relacionado con la duración de caché de determinadas respuestas negativas, conforme a las reglas DNS actuales |

Cuando cambia la zona primaria, su **número de serie** debe reflejar la nueva versión para que el secundario pueda detectar la actualización. Los detalles dependen de la implementación y de cómo se gestione la zona.

```text
1. Se modifica la zona primaria en Windows Server
2. El secundario Ubuntu/BIND9 comprueba si hay cambios
3. Se compara el número de serie SOA
4. Si procede, se transfieren los datos actualizados
```

## 6️⃣ Transferencias de zona: AXFR e IXFR

Para que un servidor secundario disponga de los datos de una zona, necesita obtenerlos desde un servidor autorizado como maestro.

- **AXFR:** transferencia completa de la zona.
- **IXFR:** transferencia incremental de los cambios, cuando ambos servidores la admiten y existen datos adecuados para realizarla.

Las transferencias de zona utilizan **TCP, puerto 53**. No debemos permitir que cualquier equipo descargue indiscriminadamente los registros internos: configuraremos los permisos para autorizar al servidor Ubuntu.

:::info[Lo realizaremos en el laboratorio]
Windows Server alojará la zona primaria `empresa.test`. Ubuntu Server, mediante BIND9, configurará una zona secundaria y solicitará su transferencia. Después añadiremos un registro en Windows y comprobaremos que aparece en Ubuntu.
:::

## 7️⃣ Cómo se representan los datos de una zona

En sistemas como **BIND9**, los registros pueden almacenarse en **ficheros de zona**. Windows Server permite administrar zonas mediante herramientas gráficas, aunque los conceptos son equivalentes.

Un registro suele contener **nombre, TTL (opcional), clase, tipo y datos**:

```text
web.empresa.test.  3600  IN  A  192.168.10.20
```

| Elemento | Significado |
|---|---|
| `web.empresa.test.` | Nombre completo |
| `3600` | TTL de 3600 segundos |
| `IN` | Clase Internet |
| `A` | Tipo de registro |
| `192.168.10.20` | Dato asociado al nombre |

Dos directivas que aparecen en el libro son:

- **`$TTL`**: establece un TTL predeterminado para los registros que no indiquen otro.
- **`$ORIGIN`**: establece el origen utilizado para completar nombres relativos.

Ejemplo didáctico de fragmento de zona:

```dns
$ORIGIN empresa.test.
$TTL 3600
web       IN A       192.168.10.20
correo    IN A       192.168.10.30
intranet  IN CNAME   web.empresa.test.
```

En este ejemplo, `web` equivale a `web.empresa.test.` porque se completa con `$ORIGIN`.

:::tip[No es necesario memorizar toda la sintaxis]
En esta unidad aprenderemos a **interpretar** los ficheros de zona y a reconocer los registros. La edición manual de archivos BIND9 se utilizará únicamente cuando sea necesaria para configurar Ubuntu como secundario.
:::

## 8️⃣ Otros registros y conceptos: ampliación

El libro también presenta registros y técnicas que conviene reconocer, aunque no configuraremos todos en el laboratorio:

| Concepto | Para qué sirve |
|---|---|
| **SRV** | Localizar servicios indicando, entre otros datos, servidor y puerto |
| **TXT** | Almacenar información textual, utilizada también en verificaciones y políticas de correo |
| **CAA** | Indicar qué autoridades certificadoras están autorizadas a emitir certificados para un dominio |
| **DNAME** | Redirigir mediante alias un subárbol de nombres DNS |
| **Glue records** | Proporcionar direcciones necesarias para alcanzar servidores de nombres en determinadas delegaciones |
| **DNSSEC** | Añadir autenticación de origen e integridad a los datos DNS mediante firmas criptográficas |

:::info[DNS dinámico]
El **DNS dinámico (DDNS)** permite actualizar registros cuando cambia una dirección IP. Servicios externos como No-IP son un ejemplo de aplicación, pero **no forman parte de nuestras prácticas obligatorias**.
:::

## 🔟 Resumen de lo aprendido

- Los servidores DNS pueden ser autoritativos, recursivos, disponer de caché o reenviar consultas.
- Una zona primaria estándar permite administrar los registros; una secundaria recibe una copia de solo lectura.
- Los registros **A, AAAA, CNAME, MX, NS, PTR y SOA** son fundamentales para comprender la administración de DNS.
- El **SOA** y las transferencias **AXFR/IXFR** intervienen en la actualización de zonas secundarias.
- En nuestro laboratorio, **Windows Server será el primario** y **Ubuntu Server con BIND9 será el secundario**.
