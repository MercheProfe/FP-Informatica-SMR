# Instalación y administración de DNS en Windows Server

En los apartados anteriores hemos aprendido cómo funciona DNS, qué tipos de servidores existen y cómo configurar un cliente Windows. Ahora instalaremos nuestro **primer servidor DNS** y comprobaremos que puede resolver los nombres de los equipos y servicios de una red local.

**RA2:** Instala servicios de resolución de nombres, describiendo sus características y aplicaciones.  
**Criterios de evaluación:** d), f) y h).  
**Entorno:** VirtualBox, `SER-Servidor` (Windows Server) y `SER-Cliente` (Windows).  
**Conocimientos previos:** UT1 DHCP y apartados 3.1–3.4 de DNS.

## 1️⃣ Escenario del laboratorio

Una pequeña empresa quiere acceder a sus servicios mediante nombres como `servidor.empresa.test` o `www.empresa.test`, sin tener que recordar direcciones IP.

Utilizaremos las máquinas virtuales existentes:

| Equipo | Función | Configuración |
|---|---|---|
| `SER-Servidor` | DHCP y DNS primario | IP fija en la red interna |
| `SER-Cliente` | Cliente de pruebas | IP y DNS manuales o recibidos por DHCP |
| `SER-Linux` | Futuro DNS secundario BIND9 | No se necesita todavía |

La zona de ejemplo será **`empresa.test`**. El dominio `.test` está reservado para pruebas y documentación; no representa un dominio público de Internet.

:::warning[Antes de modificar nada]
No cambies las IP, máscaras ni adaptadores de VirtualBox sin comprobar la configuración actual. En especial, **no conectes el servidor DHCP del laboratorio a la red física del centro**. Las pruebas locales se realizarán mediante la red interna de VirtualBox.
:::

### 🟩 Comprobación inicial

En `SER-Servidor`, abre PowerShell o Símbolo del sistema:

```powershell
ipconfig /all
```

Anota la **IPv4 fija de la tarjeta de red interna**, su máscara y el nombre del adaptador. Si hay una segunda tarjeta NAT, identifica cuál es cada una.

En `SER-Cliente`, ejecuta también `ipconfig /all` y comprueba que ambos equipos pertenecen a la misma red interna.

Comprueba la conectividad usando las IP reales:

```powershell
ping <IP_DEL_SERVIDOR>
```

`<IP_DEL_SERVIDOR>` es un marcador: sustitúyelo por la dirección real, sin escribir los signos `<` y `>`.

:::info[Conectividad y resolución]
Que funcione `ping` a una IP no significa que funcione DNS. Primero verificaremos la comunicación IP; después, la resolución de nombres.
:::

## 2️⃣ Instalación del rol Servidor DNS

Windows Server ofrece DNS como un **rol del servidor**. Su instalación añade el servicio DNS y las herramientas para administrarlo.

### 🟧 Instalación mediante el Administrador del servidor

1. Inicia sesión en `SER-Servidor` con una cuenta administradora.
2. Abre **Administrador del servidor**.
3. Selecciona **Administrar → Agregar roles y características**.
4. Elige **Instalación basada en características o en roles**.
5. Selecciona el servidor local.
6. Marca **Servidor DNS** y acepta las características de administración adicionales que se propongan.
7. Continúa hasta **Instalar**.
8. Al finalizar, abre **Herramientas → DNS**.

En la consola DNS aparecerá el nombre del servidor. Desde ella administraremos zonas, registros, reenviadores y otras propiedades.

### 🟥 Comprobación del servicio

En PowerShell puedes comprobar el estado del servicio:

```powershell
Get-Service DNS
```

El estado esperado es `Running` (en ejecución). Si el rol todavía no está instalado, el comando puede indicar que no existe el servicio.

:::tip[Dos formas de administrar DNS]
Podemos utilizar la **consola gráfica DNS** o los cmdlets de PowerShell del módulo `DnsServer`. En esta unidad utilizaremos principalmente la interfaz gráfica para comprender la estructura del servicio.
:::

## 3️⃣ Creación de una zona de búsqueda directa

Una **zona de búsqueda directa** contiene registros que permiten obtener una dirección IP a partir de un nombre.

Crearemos la zona **`empresa.test`**:

1. En la consola DNS, despliega el nombre de `SER-Servidor`.
2. Haz clic derecho en **Zonas de búsqueda directa → Zona nueva**.
3. Selecciona **Zona principal** (zona primaria estándar).
4. Escribe el nombre `empresa.test`.
5. Conserva el nombre de archivo de zona propuesto por el asistente.
6. Para este laboratorio sin Active Directory, selecciona **No admitir actualizaciones dinámicas**.
7. Finaliza el asistente.

La zona debe aparecer bajo **Zonas de búsqueda directa**. En su interior encontrarás, al menos, registros **SOA** y **NS** creados para la zona.

:::info[¿Por qué una zona primaria estándar?]
En una zona primaria estándar podemos crear y modificar registros. Más adelante configuraremos una zona secundaria en Ubuntu/BIND9 que obtendrá una copia mediante transferencia. No necesitamos instalar Active Directory para esta práctica.
:::

## 4️⃣ Creación de registros DNS

Un registro DNS relaciona un nombre con información concreta. Vamos a configurar registros de los tipos estudiados en el apartado 3.3.

### 🟩 Registro A: nombre e IPv4

1. Abre la zona `empresa.test`.
2. Haz clic derecho y selecciona **Host nuevo (A o AAAA)**.
3. Introduce `servidor` como nombre.
4. Escribe la **IP real de la interfaz interna de `SER-Servidor`**.
5. Guarda el registro.

El resultado será una asociación como esta:

```text
servidor.empresa.test  →  IPv4 interna de SER-Servidor
```

No copies una IP de ejemplo: el registro debe apuntar a la dirección real del equipo.

### 🟧 Registro CNAME: alias

Un **CNAME** permite que un nombre sea alias de otro nombre DNS.

1. En la zona, selecciona **Alias nuevo (CNAME)**.
2. Introduce `www` como alias.
3. Como nombre de destino, selecciona o escribe `servidor.empresa.test.`.
4. Guarda el registro.

```text
www.empresa.test  →  servidor.empresa.test  →  IPv4 del servidor
```

:::warning[Resolver un nombre no crea un servicio web]
Aunque `www.empresa.test` resuelva correctamente, todavía no hemos instalado un servidor web. La resolución DNS y el funcionamiento de HTTP son comprobaciones diferentes.
:::

### 🟥 Registro MX: servidor de correo

Un registro **MX** identifica el servidor que recibe correo para un dominio. Para practicar su sintaxis, podemos crear un registro MX de laboratorio, aunque **no instalaremos un servidor de correo**.

1. Crea un registro **A** llamado `correo` con una dirección IP válida del laboratorio (puede ser la del servidor si solo se simula el nombre).
2. En la zona, selecciona **Nuevo intercambiador de correo (MX)**.
3. Deja el nombre de dominio correspondiente a `empresa.test`.
4. Introduce `correo.empresa.test.` como servidor de correo.
5. Asigna una preferencia, por ejemplo `10`.

El número de preferencia permite ordenar distintos servidores MX: **el valor numérico menor tiene prioridad**.

:::info[Un MX no instala correo]
Crear el registro MX solo publica información DNS. Para recibir mensajes sería necesario instalar y configurar un servicio de correo real.
:::

## 5️⃣ Zona de búsqueda inversa y registro PTR

La **resolución inversa** permite consultar un nombre a partir de una dirección IP. En IPv4 utiliza el dominio especial `in-addr.arpa` y registros **PTR**.

Para una red ilustrativa `192.168.10.0/24`, la zona inversa sería:

```text
10.168.192.in-addr.arpa
```

En nuestro laboratorio utilizaremos **la red real**, no necesariamente la del ejemplo.

### 🟩 Creación de la zona inversa

1. En DNS, haz clic derecho en **Zonas de búsqueda inversa → Zona nueva**.
2. Selecciona **Zona principal**.
3. Elige **Zona de búsqueda inversa IPv4**.
4. Introduce el identificador de red que corresponda a tu laboratorio.
5. Conserva el archivo de zona propuesto.
6. Selecciona **No admitir actualizaciones dinámicas** y finaliza.

En una red `/24` convencional, el identificador utiliza los tres primeros octetos. Si tu red tiene otro prefijo, consulta antes cómo se organizará la zona inversa.

### 🟧 Creación del PTR

Dentro de la zona inversa, crea un **Nuevo puntero (PTR)** que relacione la IP interna de `SER-Servidor` con `servidor.empresa.test.`.

También puede crearse un PTR automáticamente al dar de alta un registro A si ya existe la zona inversa correspondiente y se marca la opción pertinente.

:::tip[Dos direcciones de resolución]
- **Directa:** `servidor.empresa.test` → dirección IPv4 (registro A).
- **Inversa:** dirección IPv4 → `servidor.empresa.test` (registro PTR).

Una asociación no implica automáticamente que exista la otra: debemos comprobar ambos registros.
:::

## 6️⃣ Configuración de SER-Cliente para utilizar nuestro DNS

El cliente debe consultar **la IP interna de `SER-Servidor`** como servidor DNS.

Tenemos dos posibilidades:

| Método | Cómo se configura | Relación con UT1 |
|---|---|---|
| Manual | Propiedades IPv4 del adaptador del cliente | Configuración directa |
| DHCP | Opción **006 — DNS Servers** del ámbito | El servidor DHCP entrega la dirección DNS |

### 🟩 Opción recomendada: aprovechar DHCP

Si el ámbito DHCP de la UT1 sigue operativo:

1. En `SER-Servidor`, abre la consola **DHCP**.
2. Localiza el ámbito de la red interna.
3. Revisa **Opciones de ámbito**.
4. Configura **006 — DNS Servers** con la IP interna de `SER-Servidor`.
5. Si procede, configura **015 — DNS Domain Name** con `empresa.test`.
6. En `SER-Cliente`, renueva la concesión DHCP:

```powershell
ipconfig /renew
ipconfig /all
```

Comprueba que el servidor DNS mostrado sea el de nuestro laboratorio. Si hay varios adaptadores, revisa el que corresponde a la red interna.

:::warning[No utilices DNS públicos como sustitutos del servidor local]
Un DNS público no conoce por defecto la zona privada `empresa.test`. Para comprobar nuestros registros, el cliente debe consultar el DNS de `SER-Servidor`. La resolución de Internet mediante reenviadores se estudiará en el apartado 3.6.
:::

## 7️⃣ Comprobación de la resolución DNS

Utilizaremos `nslookup` para consultar directamente al servidor DNS. Sustituye `IP_SERVIDOR` por la IP interna real.

### 🟩 Resolución directa

```powershell
nslookup servidor.empresa.test IP_SERVIDOR
nslookup www.empresa.test IP_SERVIDOR
nslookup -type=MX empresa.test IP_SERVIDOR
```

Resultados esperados:

- `servidor.empresa.test` devuelve la IPv4 interna del servidor.
- `www.empresa.test` muestra la relación con el alias y permite obtener la dirección de destino.
- La consulta MX devuelve `correo.empresa.test` y su preferencia.

### 🟧 Resolución inversa

```powershell
nslookup IP_DEL_SERVIDOR IP_SERVIDOR
```

Si existe el PTR correcto, la respuesta incluirá `servidor.empresa.test`.

### 🟥 Consulta utilizando la configuración del cliente

Repite una consulta **sin indicar el servidor DNS explícitamente**:

```powershell
nslookup servidor.empresa.test
```

Si esta consulta falla pero la consulta con `IP_SERVIDOR` funciona, revisa qué DNS tiene configurado el cliente.

:::info[Mensajes que pueden confundir]
`nslookup` puede mostrar `Servidor: Unknown` cuando no puede resolver inversamente el nombre del servidor DNS consultado. Ese mensaje **no demuestra por sí solo que la consulta haya fallado**: revisa también si se obtiene la respuesta solicitada.
:::

## 8️⃣ Diagnóstico de incidencias frecuentes

| Síntoma | Posible causa | Primera comprobación |
|---|---|---|
| No responde `ping` a la IP del servidor | Problema de red, interfaz o cortafuegos ICMP | `ipconfig /all`, adaptadores y conectividad |
| `nslookup` agota el tiempo de espera | DNS detenido, IP incorrecta, firewall o conectividad | `Get-Service DNS` y servidor consultado |
| El nombre no existe | Zona o registro ausente, o nombre mal escrito | Consola DNS y FQDN |
| La consulta directa funciona y la inversa falla | Falta zona inversa o PTR | Zona inversa y registro PTR |
| Consulta explícita correcta, consulta normal incorrecta | Cliente usa otro DNS | `ipconfig /all` y opción DHCP 006 |
| El alias resuelve pero la web no abre | No hay servicio HTTP operativo | Distinguir DNS de servidor web |

DNS utiliza normalmente **UDP 53** y también **TCP 53** en determinadas operaciones. En el apartado de transferencias veremos especialmente el uso de TCP.

## 🔟 Comprobación final

Antes de continuar con el apartado 3.6, debemos poder verificar lo siguiente:

- El rol DNS está instalado y su servicio se encuentra en ejecución.
- Existe una zona primaria estándar `empresa.test`.
- Los registros A, CNAME y MX responden correctamente.
- Existe una zona inversa con un PTR para el servidor.
- `SER-Cliente` utiliza el DNS del laboratorio, preferentemente mediante DHCP.
- Las consultas directas e inversas funcionan desde el cliente.
